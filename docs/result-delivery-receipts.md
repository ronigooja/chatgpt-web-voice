# Result delivery receipts

Applies to authenticated downstream result delivery requests when the service has durable receipt storage configured. `/v1/health` advertises `result_deliveries.version="v1"`, `max_text_bytes=8000`, and `applied_evidence="local_transport_writes_and_durable_receipt"` only to authenticated clients when storage is wired.

- `POST /v1/voice/sessions/{id}/result-deliveries`: exact JSON fields `media_generation` (positive integer), `delivery_id` (1–128 ASCII letters/digits/`_.-`), `content_hash` (lowercase SHA-256 hex of UTF-8 text), `text` (nonblank, at most 8000 UTF-8 bytes). Body limit: 64 KiB; duplicate/unknown fields, malformed UTF-8 and unpaired surrogate escapes are rejected.
- `GET /v1/voice/sessions/{id}/result-deliveries/{delivery_id}?media_generation=N`: read-only receipt lookup; no live session required. Missing or differently owned identities return 404.
- Successful responses contain exactly `media_generation`, `delivery_id`, `content_hash`, `state`. States: `pending`, `applied`, `unknown`, `rejected`. Invalid payloads return 400; immutable content conflicts or stale media generations return 409; persistence failures return 503.

`voice_result_receipts` owns immutable payloads under the complete owner/session/media-generation/delivery identity. Insert and atomic attempt claim precede transport dispatch; finalization is fenced by the complete identity and attempt. Existing receipts never authorize replay. Startup changes abandoned pending/inflight rows to unknown; read-only lookup projects inflight as unknown without writes. New receipts require the current owned binding and exact media generation. Existing owned receipts remain reconcilable after hangup or replacement.

`applied` means every local transport write returned success and its terminal state persisted, never upstream interpretation, consumption, or speech. AVAS uses the context helper's UTF-8-safe 500-byte frames; any attempted frame followed by failure is unknown. WM uses the existing typed user-text envelope and synchronous active-leg DataChannel writes, not bridge queue acceptance. Definitely pre-write failures are rejected. Persistence failure after a write is unknown and never replayed, including when a follow-up unknown update also fails.

Single-process binding locking excludes generation replacement/release during dispatch; relay leg locking excludes WM leg swap during the actual write. No SQLite transaction spans network IO. The supported deployment is one gateway process per database; startup recovery is not a multi-process lease protocol. Slow transport writes serialize binding operations. Crash tests simulate durable pending/inflight states; they do not kill a process or emulate hardware durability failures.

## Opening creation receipts

Applies only to AVAS creation with opening items: `content_hash` is lowercase SHA-256 hex of Go `json.Marshal` of the ordered struct `{kind,version,items}`, with each item ordered `{role,text}`, before transformation to `initial_items`. This matches Zoe's canonical serialization (including Go HTML escaping); it is not a hash of arbitrary raw request bytes. Zoe's internal `PendingResults` field is excluded from JSON. Unknown request fields are rejected.

Only the current invocation's successful initial-items creation plus durable metadata finalization may return `applied:true`, `silent:true`, matching `version` and `content_hash`. No upstream consumption or speech is attested. Metadata failure, absent media generation, or replaced/closed media omits the hash and cannot acknowledge availability. WM retains `silent:"unverified"` and no hash proof. Creation request/outcome non-idempotency and lost-response handling are unchanged; old creation responses are never replayed.

For fresh databases and in-place upgrades from commit `411251c` (`main-411251c`), startup migration creates `voice_result_receipts` and adds missing `call_sessions.opening_context_hash` (default `''`) and `opening_context_generation` (default `0`) without resetting existing account or bridge rows. These columns bind metadata to the concrete owner/session/media generation/version. Finalization requires an active durable media identity and the exact current binding. Existing-session AVAS versions are checked before creation or context injection: same version requires the stored matching hash, and missing hashes or different content conflict. Single-process opening locking serializes AVAS preflight through finalization without a SQL transaction across the network; identical finalization does not increment context metrics twice. A new creation still creates media rather than replaying an old response.
